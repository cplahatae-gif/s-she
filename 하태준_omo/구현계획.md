# SAFEPLAY 「마지막 자물쇠」 독립 구현계획

## 요약

- 목표: `하태준_omo` 안에서 작업자 시점의 단일 시나리오를 처음부터 결과와 다시 연습까지 완성한다.
- 결과물: 독립 실행 앱, 고정 규칙 계약, `node:test` 검사, 자산 적격성 기록, 움직임 보정 기록, 브라우저 검증 증거다.
- 예상 규모: 중간.
- 주요 위험: 제공 자산이 보행과 합성 기준을 통과하지 못하면 기능 구현은 끝낼 수 있지만 자산 기반 화면의 시각 완료는 보류된다.

## 근거와 정리된 불일치

- 이번 구현 루트는 사용자가 지정한 `하태준_omo`다. 이전 작업자의 루트, 공용 루트, 기본 `.omo/plans` 저장 규칙보다 이 지정이 우선한다.
- `node --test 하태준/tests/*.test.mjs`의 기존 6개 검사는 현재 통과하지만 새 앱의 증거가 아니다. PRD의 실행 가능한 검사가 없다는 표현은 새 구현 기준으로만 해석한다.
- `하태준_omo/docs/contract.md`, `하태준_omo/docs/결정사항.md`, `하태준_omo/reference`는 새로 만들 대상이다. 누락된 공용 문서를 복원하지 않는다.
- 이 계획 작성 단계에서는 `하태준_omo/구현계획.md` 외의 소스, 검사, 자산을 수정하지 않는다.
- Metis 사전 검토에서 지적한 판정 우선순위, 확인 무효화, 거리 재검사, 복귀 목적지, 사고 시간의 측정 시작과 끝, 자산 부족 시 시각 완료 보류를 고정 결정과 검증 항목에 반영했다.

## 범위

### 반드시 포함

- 저장소 루트에서 정적 서버를 열고 `http://127.0.0.1:8770/하태준_omo/`로 실행되는 하이퍼텍스트 마크업 언어(HTML), 종속형 시트(CSS), 자바스크립트 ES 모듈(ES modules) 기반 앱을 만든다.
- 전체 공장 전경, 작업 요청, 현장 이동, 네 대상 조사, 안전조치, 작업 진입 판정, 사고, 되감기, 성공, 결과, 공장 복귀, 이어하기, 다시 연습을 한 시나리오로 연결한다.
- 한 판 상태와 화면 상태는 `src/app.js` 한 곳에서 소유한다. 현장, 공장 전경, 패널은 입력과 표시만 담당하고 콜백(callback)으로 요청한다.
- 규칙 모듈은 문서 객체 모델(DOM), Phaser(브라우저 2D 게임 엔진), 네트워크 없이 결정론적으로 동작한다.
- 방향키와 A/D 이동, E 조사, Tab/Enter/Space 패널 조작, Escape로 닫을 수 있는 일반 패널, 포커스 이동과 복원을 제공한다.
- 단일 수평 보행선의 투영 좌표로 네 대상의 작업자 정지점과 거리를 계산한다. 장애물과 자유로운 상하 이동은 없다.
- 움직임 줄이기 설정, 자산 오류 안내와 재시도, 창 비활성화 시 입력 해제, 중복 입력 방지를 포함한다.
- 기능 임시 화면, 자산 적격성, 정적 합성, 이동, 보행, 카메라 순서의 품질 게이트를 통과한 뒤에만 다음 단계로 넘어간다.
- 공개 규칙 계약은 `하태준_omo/tests`의 Node.js(자바스크립트 실행 환경) 내장 검사기로 검증하고, 실제 사용자 흐름은 브라우저에서 검증한다.

- `하태준`, 공용 `src`, 공용 `assets`, 공용 `docs`, `vendor`를 수정하거나 새 독립 구현으로 가져와 편집하지 않는다. 공용 자산은 적격성 통과 후 상대 경로로 읽기만 한다.
- `하태준/assets/stage-background.png`, `하태준/assets/worker-walk.png`, `하태준/assets/assets.json`은 참고 후보일 뿐이다. 검증 없이 복사하거나 합격 자산으로 간주하지 않는다.
- 자산이 없거나 탈락했다는 이유로 이미지를 생성하지 않는다. 사용자가 제공한 파일도 자산 게이트를 통과해야 사용한다.
- 외부 AI(인공지능), 서버 응용 프로그래밍 인터페이스(API), 로그인, 점수 저장, 추가 시나리오, 무전 압박, 제한 시간, 작업 후 잠금 해제와 재가동, 모바일 전용 조작, 3D, Blender, Three.js를 추가하지 않는다.
- 외부 AI 실패처럼 보이는 `기본 설명 사용`, 로딩 중 AI 문구, AI 대체 경로를 화면에 넣지 않는다. 결과 설명은 항상 고정 문구다.
- 실제 설비 절차를 승인하거나 추정하지 않는다. 차단 위치와 행동은 게임용 예시라는 고정 안내를 유지한다.
- 새 실행 환경(runtime) 의존성, 새 검사 의존성, 번들러(bundler, 여러 파일을 묶는 도구), 패키지 관리 설정을 추가하지 않는다.
- 전역 객체에 검사 전용 명령을 달거나 운영 흐름을 건너뛰는 검사 치트 코드를 두지 않는다.
- 자동 커밋, 푸시, 외부 이슈 등록을 하지 않는다.

## 고정 구현 결정

### 로컬 계약

`src/scenario/scenario.mjs`의 공개 계약은 다음으로 고정한다.

- 대상 식별자: `work-access`, `control-panel`, `energy-isolator`, `verification-point`.
- 행동 식별자: `isolate-energy`, `attach-personal-lock`, `attach-wrong-lock`, `attach-tag`, `clear-residual-energy`, `verify-isolation`, `enter-work`.
- 공개 함수: `createRun()`, `inspect(run, targetId)`, `applyAction(run, actionId)`, `judgeEntry(run)`, `rewind(run)`.
- `run.observed`는 `Set`이며 중복 조사를 한 번만 기록한다.
- `run.attempts`는 유효한 `enter-work` 요청 한 번마다 정확히 1 증가한다. 조사, 안전조치, 보완 선택, 무효 요청, 완료 뒤 요청은 증가시키지 않는다.
- `run.rewinds`는 사고 카드의 유효한 되감기 한 번마다 정확히 1 증가한다.
- `run.completed`는 성공 판정 때만 `true`가 된다.
- `run.safety`는 `{ isolated: boolean, lockState: 'none' | 'wrong' | 'valid', tagged: boolean, residualCleared: boolean, verification: 'unperformed' | 'failed' | 'passed' }`로 고정한다. 의미가 겹치는 `locked`, `lockPresent`, `verified` 보조 불리언은 만들지 않는다.
- 문자열이 아닌 대상 또는 행동 식별자는 `TypeError`, 허용 목록에 없는 문자열은 `RangeError`로 거절한다. 거절 전후 `run` 전체와 모든 카운터는 동일해야 한다.
- 현재 단계에서 허용되지 않은 유효 식별자는 `{ kind: 'blocked', reason }`를 반환하며 상태와 카운터를 바꾸지 않는다.

안전조치와 확인 무효화 규칙은 다음으로 고정한다.

- `isolate-energy`가 `false`에서 `true`로 바뀌면 `verification`을 `unperformed`로 만든다. 이미 `true`인 반복 요청은 멱등(idempotent)이며 확인 결과를 바꾸지 않는다.
- `attach-personal-lock`은 차단 뒤에만 가능하고 `lockState`를 `valid`로 바꾼다. `attach-wrong-lock`은 차단 뒤에만 가능하고 `lockState`를 `wrong`으로 바꾼다. 잠금 상태가 실제로 바뀌면 `verification`을 `unperformed`로 만든다.
- 잠금 변경은 `tagged`와 `residualCleared`를 자동 완료하거나 자동 해제하지 않는다. 잠금 보완 뒤 확인만 다시 수행한다.
- `attach-tag`는 `lockState === 'valid'`일 때만 가능하다. 표지 변경은 에너지 경계 변경이 아니므로 기존 확인 결과를 무효화하지 않는다.
- `clear-residual-energy`는 실제 차단과 유효 잠금 뒤에만 가능하다. `false`에서 `true`로 바뀔 때 `verification`을 `unperformed`로 만든다. 반복 요청은 멱등이다.
- `verify-isolation`은 차단, 유효 잠금, 잔류 에너지 조치가 모두 참이면 `passed`, 하나라도 아니면 `failed`로 기록한다. 실패는 사용자에게 보이는 상태이며 보완 뒤 다시 확인할 수 있다.
- 조사만으로 어떤 안전 상태도 바꾸지 않는다. 되감기도 어떤 안전 상태도 바꾸지 않는다.

작업 진입 판정 순서는 다음으로 고정한다. 위 항목이 먼저 일치하면 아래 항목을 평가하지 않는다.

1. `isolated === false`: `wrong`과 `accident`, 정지 표시는 차단과 잠금 확인을 대신하지 못한다는 고정 이유.
2. `lockState !== 'valid'`: `wrong`과 `accident`, 자물쇠가 보이는 것과 유효 잠금이 다르다는 고정 이유.
3. 차단과 유효 잠금 뒤 `verification === 'failed'`: `blocked`와 `verification-failed`, 차단이 확인되지 않아 작업을 보류한다는 고정 이유.
4. `tagged === false`, `residualCleared === false`, `verification !== 'passed'` 중 하나 이상: `incomplete`, 빠진 필수 조치를 완료하라는 고정 이유.
5. 모두 충족: `success`, `completed = true`, 안전한 이물질 제거와 결과로 이동.

런타임 핵심 문구는 다음으로 고정한다. 문구를 네트워크 응답으로 교체하지 않는다.

- 작업 요청: `컨베이어 점검구 안에 이물질이 끼었습니다. 제거 작업을 맡았습니다. 벨트는 멈춰 있지만, 작업에 들어가기 전에 직접 안전을 확보해야 합니다.`
- 차단 누락: `벨트가 멈춰 있어도 다시 움직일 수 있습니다. 정지 표시는 에너지 차단과 잠금의 확인을 대신하지 못합니다.`
- 잠금 누락 또는 잘못된 잠금: `자물쇠가 보이는 것만으로 안전해지지 않습니다. 해당 설비의 에너지를 차단하고 그 차단 상태를 유지하도록 잠가야 합니다.`
- 기록된 확인 실패: `차단이 확인되지 않았습니다. 현장 절차에 따라 원인을 확인하고 안전조치를 보완하세요.`
- 일반 미완료: `아직 필수 조치가 끝나지 않았습니다. 빠진 단계를 완료한 뒤 작업에 들어가세요.`
- 사고 제목과 본문: `벨트가 움직였습니다.`와 `이물질을 제거하려던 순간 컨베이어가 불시에 움직였습니다.`
- 결과 제목: `안전을 확인하고 작업에 들어갔습니다.`
- 결과 설명: `멈춰 있다는 표시를 믿고 들어가지 않았습니다. 직접 차단하고 본인 자물쇠·표지를 체결한 뒤, 차단을 확인하고 작업에 들어갔습니다.`
- 예시 안내: `화면 속 차단 지점과 안전조치는 게임용 예시입니다. 실제 작업에서는 승인된 현장별 설비 절차를 따릅니다.`
- 결과에는 설명 출처 라벨을 두지 않는다. `기본 설명 사용`, AI 대체, 생성 중 문구를 표시하지 않는다.

화면 상태는 `overview`, `stage-loading`, `brief`, `stage`, `inspection`, `entry-check`, `accident-playing`, `accident-card`, `result`, `asset-error`로 고정한다. `src/app.js`만 `run`, `screen`, `activeTargetId`를 변경한다. Phaser 장면은 위치, 속도, 방향, 카메라처럼 그리기에 필요한 일시 상태만 가진다. 패널은 전달받은 스냅숏(snapshot)만 표시한다.

현장 조사 콜백은 `targetId`만 전달한다. 앱은 콜백의 거리 자료를 신뢰하지 않고 `screen === 'stage'`, 알려진 대상, `stage.snapshot().x`가 유한함, `Math.abs(stage.snapshot().x - layout.targets[targetId].standX) <= interactionRadius`를 직접 다시 확인한 뒤 `activeTargetId`를 설정한다. 패널 행동은 `screen`이 `inspection` 또는 `entry-check`이고, 요청 대상이 `activeTargetId`와 같고, 패널이 열린 동안 무대 이동이 잠겨 있으며, 현재 `stage.snapshot()`으로 같은 거리 검사를 다시 통과하고, 행동 식별자가 해당 대상의 허용 행동 목록에 속할 때만 규칙 모듈에 전달한다. 실패한 요청은 고정 안내만 표시하고 `run`을 바꾸지 않는다.

한 개의 수평 보행선에 대상별 `standX`를 둔다. 거리 판정은 수평 투영 거리만 사용하고, 대상 이미지의 중심이나 원근상 세로 위치는 판정에 사용하지 않는다. 이 결정은 장애물이 없는 단일 통로라는 게임용 예시 배치에만 적용한다.

사고 재현은 일반 모드에서 붉은 화면 층(layer)과 350밀리초 흔들림, 900밀리초 암전, 1,300밀리초 안에 사고 카드 표시로 고정한다. 움직임 줄이기에서는 점멸과 흔들림 없이 붉은 고정 화면 층, 500밀리초 암전, 900밀리초 안에 사고 카드 표시로 고정한다. 어느 경로도 유효한 진입 제출부터 사고 카드가 보이고 되감기 버튼에 포커스(Focus)가 놓일 때까지 6초를 넘기지 않는다.

공장 복귀는 `accident-playing`과 `accident-card`에서 금지한다. 일반 패널에서 공장으로 복귀하면 패널과 `activeTargetId`를 닫고 무대를 정지한다. 다시 현장에 들어오면 미완료 판은 저장 위치의 `stage`, 완료된 판은 `result`로 복원한다. 일시 패널을 자동으로 다시 열지 않는다.

움직임 임시 보정 기준은 입력 시작 뒤 속도 변화가 처음 관찰되는 시점과 키 해제 뒤 감속이 시작되는 시점을 각각 100밀리초 이내로 잡는다. 100밀리초는 완전 정지가 아니라 반응 개시 기준이다. 접지 중 발 미끄러짐은 부츠 길이의 10% 이하, 발과 바닥의 간격 또는 침범은 화면상 신체 높이의 1% 이하를 임시 합격선으로 둔다. 발이 가려져 측정할 수 없으면 보행 게이트는 실패다.

진단은 `?diagnostics=1`에서만 보이는 읽기 전용 패널로 제한한다. 패널은 화면 상태, 작업자 x, 입력 방향, 속도, 가까운 대상과 거리, 카메라 x, 현재 보행 프레임(frame), 좌우 발바닥 월드 x/y, 접지 발, 바닥 y, 사고 시작 시각과 카드 표시 경과시간만 표시한다. 상태 변경 버튼, 시간 건너뛰기, 전역 검사 함수는 두지 않는다.

## 검증 전략

### 5. 임시 도형으로 전체 기능 흐름 연결

해야 할 일:

- 작업 2의 `하태준_omo/src/app.js`를 확장하고 새 파일 `하태준_omo/src/site/stage.js`, `하태준_omo/src/ui/diagnostics.js`를 만들어 작업 2의 셸, 작업 3의 규칙, 작업 4의 배치를 연결한다.
- Phaser 도형으로 공장 진입부터 결과까지 한 판을 먼저 완성한다. 배경은 산업 현장임을 구분할 수 있는 중립 도형, 작업자는 한 개의 명확한 도형, 대상은 서로 다른 명칭과 표식으로 표시한다. 임시 화면임을 사용자에게 알린다.
