# 여섯 단계 실습·이동 수정 QA

2026-10-09, 이번 수정 턴에서 부모 에이전트가 실제 Chrome 1280×720과 `http://127.0.0.1:8781`에서 수행한 수동 검증을 기록한다. 이 보고서는 해당 실행자의 전달 증거를 정리한 것이며, 이전 자유 행동 버전의 QA 결과를 재사용하지 않는다. HEAD는 `9d895b23e3d56dbefb5b9bf5b60232bf87a0c0d8`이며 아래 증거는 그 위의 로컬 작업 트리에 해당한다. 스테이징·커밋·푸시는 수행하지 않았다.

## 시나리오와 결과 화면

- 작업반장의 이물질 제거 지시와 첫 질문을 확인했다. [01-foreman.png](01-foreman.png). 네 보기 화면은 새로 갱신한 [10-final-screen.png](10-final-screen.png)에서 확인한다.
- 여섯 단계의 각 질문에서 네 보기를 확인하고 정답을 순서대로 선택해 최종 제거 완료에 도달했다. native 접근성 상태에서 완료와 선택 10회·되감기 1회를 관찰했다. 정답 6회와 다른 설비 잠금·표지 생략·트라이아웃 실패 무시·제거 전 잠금 해제의 오답 4회를 포함한다. 이때 초기 캡처는 앞선 질문 화면이어서 완료 증거로 사용하지 않는다.
- 다른 설비 잠금은 대상 불일치 결과, 표지 생략은 식별 누락 결과, 트라이아웃 실패는 차단 이상과 접근 보류 결과를 보여주었다. 실행자가 이번 턴의 native 접근성 상태에서 관찰한 결과이며, 모든 오답을 같은 사고로 처리하지 않았다.
- 같은 턴의 앞선 실행에서 비상정지만으로 완료 처리와 모호한 오퍼레이터 전달도 각각 다른 비사고 결과를 확인했다. 비사고 결과를 열어 둔 상태로 공장뷰를 왕복해도 해당 결과를 복원했다.
- 최종 타이머 수정 후 제거 전 잠금 해제 사고 → 공장뷰 왕복 → 사고 결과 복원 → 되감기를 수행했다. 여섯 번째 단계 직전의 완료 조치 다섯 개를 유지했고 기록은 선택 9회·되감기 1회였다. 같은 질문에서 올바른 제거를 선택해 선택 10회·되감기 1회로 완료한 상태를 이번 턴의 native 접근성 정보로 확인했다. 사고 결과의 유효한 화면 캡처는 남기지 못했다.
- 다시 연습에서 선택·되감기 기록이 0/0으로 초기화되었다. 움직임 줄이기 설정에서도 운전 중 접근의 사고 카드와 되감기가 작동했다.
- 완료 증거를 다시 촬영하는 실행에서는 실제 이동으로 여섯 단계를 재수행했고 정답 6회·되감기 0회로 완료했다. 최신 [08-complete.png](08-complete.png)는 화면을 새로 갱신한 뒤 실행자가 실제 완료 카드를 직접 확인한 이미지다. [completion-dom.txt](completion-dom.txt)의 접근성·DOM 증거도 완료 조치 여섯 개와 6/0 기록을 확인한다. 이 재촬영의 6/0 기록과 앞선 오답 포함 실행의 10/1 기록은 서로 다른 실습이다.

캡처 도구가 앞선 프레임을 반환한 사례가 있었다. `02-four-choices.png`는 실제 공장뷰, `04-wrong-lock.png`는 MCC 질문, `06-tryout-failure.png`는 트라이아웃 질문, `07-accident.png`는 사고 전 조치 5/6·선택 9회·되감기 0회의 장면이다. 이 네 이미지는 결과 증거로 인용하지 않으며, 이름과 다른 이전 화면의 맥락만 담는다. 초기 `08-complete.png`도 여섯 번째 질문을 담았으나 위 재촬영의 검증된 완료 이미지로 교체했다. 최종 `08-complete.png`와 `10-final-screen.png`는 별도의 새 화면 요청 뒤 실제 내용을 직접 확인했다.

## 이동과 걷기 표현

- 실제 방향키 유지 입력으로 오른쪽 2.5초 동안 x=1344 → 1841, 다음 3.8초 동안 x=2601까지 이동했다. 왼쪽 5.5초 뒤 x=1502, 다음 4.3초 뒤 x=641을 확인했다. 가속·감속을 포함하며 유지 중 속도는 약 200px/s였다. [03-walk.png](03-walk.png), [05-walk-left.png](05-walk-left.png).
- 걷기 표본의 DOM 관찰에서 위상 순서 `1,2,3,4,5,6,7,0`, 유지 중 속도 200, 바닥 기준 y=619.2를 확인했다. 오른쪽 걷기 이미지 `walk-right-0.png`부터 `walk-right-17.png`까지와 `walk-sample-0.png`부터 `walk-sample-9.png`까지를 남겼다. 실행자가 프레임 2·6·0과 정지 자세를 직접 관찰했고, 인물 높이와 바닥 접촉이 안정적이며 과장된 상하 흔들림이 없음을 확인했다.
- 키를 놓은 뒤 속도 0을 확인했다. 왼쪽 경계 x=76, 오른쪽 경계 x=3124에서 정지했고, 오른쪽 이동 버튼을 Space로 조작해 x=76 → 136으로 이동했다. 좌표·속도는 실행 중 상태 관찰로 확인했으며 [09-right-boundary.png](09-right-boundary.png)는 경계 장면의 맥락 자료다.
- 캔버스 밖으로 포커스를 옮겼을 때 x=2935·속도 0이 유지되었고, 이후 유지 입력을 해제해도 위치가 바뀌지 않았다. 실제 창 blur나 hidden 전환 수동 검증과는 구분한다.

초기 실행에서는 다른 창에 가려진 Chrome의 RAF 정체로 행동 장면이 끝나지 않는 문제가 발견되었다. 행동 완료를 독립 타이머로 관리하고 Phaser의 `fps.forceSetTimeOut`을 60fps 설정에 적용한 뒤, 위의 유지 이동과 사고 왕복·되감기·완료를 최종 origin에서 다시 실제 실행했다.

## 자동 검사와 콘솔

최종 변경 이후 부모가 재실행한 시나리오 14개·이동 6개·서버 22개, 합계 42개 논리 검사가 모두 통과했으며 종료 코드 0이다. Node TAP의 29개 표시는 시나리오 파일을 한 래퍼로 집계하기 때문에 내부의 사용자 정의 검사 14개를 따로 포함한 총 논리 사례 수와 다르다.

`app`, `stage`, `overview`, `scenario`, `layout`, `motion`, `feedback`, `server` 여덟 모듈의 구문 검사와 `git diff --check`도 최종 통과했다.

8781의 최종 실행에서 새로운 콘솔 오류는 관찰되지 않았다. 이전 8770 origin에서 신형 `STEPS` export가 아직 없던 시점의 오류 로그를 관찰했지만, 새 origin의 최종 실행 오류로 집계하지 않는다.

## 남은 한계

- 새 걷기 자료는 생성 이미지의 여덟 개 이산 자세를 사용한다. 4/8 부근 위상의 상하 자세는 완전히 자연스럽지 않으며 개선 여지가 있다.
- 발의 미끄러짐 비율을 수치로 측정하지 않았다. 바닥 기준·걷기 표본·정지 높이 관찰은 정량적인 보행 품질 측정을 대신하지 않는다.
- 실제 창 blur·hidden 전환은 수동으로 확인하지 않았다. 입력 해제 관련 순수 함수 검사는 있으나 해당 브라우저 수동 검증의 증거는 아니다.
- 이 실습은 예시 설비이며 실제 MCC·작업 권한·잔류 에너지 처리·트라이아웃 절차를 승인한 교육자료가 아니다.

신규 걷기 자료의 정확한 생성 프롬프트는 [walk-v2-prompts.md](../../assets/walk-v2-prompts.md)에 있다. 기존 이미지 자산은 보존했다.
